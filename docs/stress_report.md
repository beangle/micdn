# micdn HTTP 压测对比报告（2026-08-13）

目的：对比五次演进对四场景的吞吐影响——基线 `490a455`（每次请求同步 stat）→ `8ddfd47`（`sendFile` 必填调用方预取的 `FileInfo`、www `get()` 异步 stat 并复用）→ **发布期文件索引 `59c8320`**（deploy 后构建段树索引，请求期存在性判定 0 stat）→ `2f0a386`（部署期预压缩 + `gzSize` 索引）→ `8f6d182`（热路径去 `buildPath` + `segmentPath` 单趟扫描）。

## 修订版说明（每次压测对应的代码状态）

| 修订版 | 改动内容 |
|--------|----------|
| `490a455`（基线） | 无索引：每请求 stat 判定存在性；gzip 后台线程按需生成，请求线程 `getFileInfo(gz)` 现查 |
| `8ddfd47` | 存在性判定改异步 stat 通道（404 回落 ~10%）；gzip 仍请求期 stat |
| 索引版 `59c8320` | 发布期文件索引：存在性 / 目录折叠 / try-file 回退 0 stat；gzip 命中仍保留 1 次 `getFileInfo(gz)` |
| `2f0a386`（本轮） | gzip 改**部署期预压缩**（www auto-gzip / asset 非 `<dir>` 强制），`gzSize` 随索引同趟登记（gzip 0 stat）；共享 `FileIndex`（asset 复用）；`sendFile` 收 `IndexedFileInfo`；asset `AssetFile` 化、移除逗号拼接 |
| `adb4eab` | 热路径去 `buildPath`：`FileIndex` 构建期缓存 `rootDir`，索引命中直接拼接物理路径；`repositoryPath` 直拼已归一化 segments（微基准 ~213ns → ~54ns） |
| `8f6d182`（本轮） | `segmentPath` 单趟字节扫描零拷贝切片替代 `std.string.split`（微基准快 30–40%） |

## 分析

1. **存在性判定归零是最坏路径的最大收益**：目录 → index.html 从"5 次 stat"到"0 stat"（索引内查 `index.html`），RPS +73.7%（vs 基线 `490a455`）、平均延迟 4.36→2.88ms。发布期索引把"如何快速判断文件是否存在"从每次请求的 stat 前移为部署时的一次目录遍历。
2. **404 由回落转回升**：上一版 404 因异步 stat 通道开销回落 10%，索引版断链即 404（`isStaticAsset` 短路，0 stat），回升到 14.5k（+18.7% vs `8ddfd47`，+6.4% vs 基线）。
3. **文件命中受带宽/IO 制约**：138KB 响应约 1.9–2.1 GB/s，stat 减少后吞吐仍受读盘与网络限制（+29.9% vs `8ddfd47`），不如小响应场景明显。
4. **gzip 命中已降到 0 stat**：gzip 改为部署期预压缩，sidecar 大小随索引同趟登记（`gzSize` 挂源文件节点，`.gz` 不建节点），请求期一次 `find` 同时取得源与预压缩信息。实测 gzip 命中 24 458 → **32 286 RPS（+32.0% vs 索引版 `59c8320`）**，为 `2f0a386` 唯一的结构性提升场景。
5. **索引代价**：启动期每 doc/bundle 一次目录遍历（小规模毫秒级，输出汇总日志）；autodeploy 重建联动已实现；内存为轻量 `IndexedFileInfo`（约 32B/条，含 `gzSize`）+ 段树节点，10 万文件量级 6–8MB。
6. **非 gz 场景与索引版 `59c8320` 基本持平**：`2f0a386` 非 gz 三场景均在噪声带内（最坏 +2.7%、文件 +0.4%、404 +1.5%）。`8f6d182` 在索引版基础上：最坏路径 +9.2%、404 +4.6%（每请求路径处理减负）；文件命中 −5.0%——该场景带宽受限（约 2.1 GB/s），两提交又纯为 CPU 减负，理论不应回落，三轮记录一致低于索引版（15.4k–15.6k vs 16.2k–16.3k），幅度超出同日波动带，暂判为编译/内存页布局差异，建议后续以 perf 复核。
7. **perf 佐证**：`buildPath`（此前 1.78%）与 `segmentPath`（此前 3.13%）双双退出热点列表；当前前列为 `memmove` 6.1%（响应拷贝）、GC 各函数合计约 11%（mark/smallAlloc/allocPages/clear 等）、eventcore 驱动 `_d_cast` 约 4.1%、`TCPConnection` postblit/dtor 约 3.3%——每请求的路径处理已不再是可见开销。
